# Требования

## Роли

| Роль | Назначение |
|---|---|
| CLIENT | Создание и просмотр своего заказа |
| MASTER | Работа с назначенными заказами |
| OPERATOR | Подтверждение и распределение заказов |
| ADMIN | Управление системой и доступом |

## Пользовательские сценарии

| ID | Сценарий | Роль |
|---|---|---|
| UC-01 | Посмотреть каталог услуг | Клиент |
| UC-02 | Рассчитать предварительную стоимость | Клиент |
| UC-03 | Создать заказ | Клиент |
| UC-04 | Посмотреть или отменить заказ | Клиент |
| UC-05 | Подтвердить заказ | Оператор |
| UC-06 | Назначить мастера и время | Оператор |
| UC-07 | Посмотреть назначенные работы | Мастер |
| UC-08 | Изменить статус выполнения | Мастер |
| UC-09 | Управлять услугами и ценами | Администратор |
| UC-10 | Посмотреть статистику | Владелец |

|---|---|---|

| FR-02 | Система показывает состав предварительной цены | MVP |
| FR-03 | Система принимает имя, телефон, адрес, услугу и желаемое время | Прототип |
| FR-04 | Система создаёт заказ со статусом `new` | Прототип |
| FR-05 | Система возвращает заказ по идентификатору | Прототип |
| FR-06 | Система хранит историю статусов | MVP |
| FR-07 | Оператор подтверждает или отклоняет заказ | MVP |
| FR-08 | Система проверяет доступность временного слота | MVP |
| FR-09 | Оператор назначает подходящего мастера | MVP |
| FR-10 | Мастер видит только назначенные ему заказы | MVP |
| FR-11 | Мастер отмечает начало и завершение работы | MVP |
| FR-12 | Клиент и мастер получают уведомления | MVP |
| FR-13 | Система хранит факт и способ оплаты | Позже |
| FR-14 | Клиент оставляет оценку и комментарий | Позже |

| FR-18 | Система формирует статистику заказов и выручки | Позже |

| FR-20 | Повторная ошибка публикации не удаляет событие | Прототип |

## Бизнес-правила

| ID | Правило |
|---|---|
| BR-01 | Стоимость до подтверждения оператором является предварительной |
| BR-02 | Желаемое время заказа должно находиться в будущем |
| BR-03 | Один активный слот нельзя назначить двум заказам |
| BR-04 | Подтвердить заказ может оператор или администратор |
| BR-05 | Назначить мастера может оператор или администратор |
| BR-06 | Мастер видит телефон и адрес только назначенного заказа |
| BR-07 | Для мастера, оператора и администратора обязательна 2FA |
| BR-08 | Отменённый заказ нельзя вернуть в работу без нового подтверждения |
| BR-09 | Каждое изменение статуса записывается в историю |
| BR-10 | События RabbitMQ не содержат имя, телефон и адрес клиента |

## Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-01 | 95 процентов внутренних запросов выполняются не дольше 500 мс без учёта внешних систем |
| NFR-02 | Целевая доступность рабочей системы составляет 99,5 процента в месяц |
| NFR-03 | Внешний обмен выполняется только по TLS |
| NFR-04 | Доступ проверяется по роли и владельцу объекта |
| NFR-05 | Телефоны и адреса не записываются в технические логи |
| NFR-06 | Резервная копия базы создаётся не реже одного раза в сутки |
| NFR-07 | Целевой RPO составляет 24 часа, RTO составляет 4 часа |
| NFR-08 | Изменения контрактов имеют версию и сохраняют обратную совместимость в пределах основной версии |
| NFR-09 | Система поддерживает горизонтальный запуск нескольких экземпляров API |
| NFR-10 | Интерфейс работает на экране телефона без горизонтальной прокрутки |

## Критерии приёмки прототипа

| ID | Критерий |
|---|---|
| AC-01 | Корректный `POST /api/v1/orders` возвращает код 201 |
| AC-02 | Новый заказ имеет статус `new` и хранится в PostgreSQL |
| AC-03 | `GET /api/v1/orders/{orderId}` возвращает созданный заказ |
| AC-04 | Запрос неизвестного заказа возвращает код 404 |
| AC-05 | Ошибка входных данных возвращает код 422 |
| AC-06 | Создание заказа добавляет запись в transactional outbox |
| AC-07 | Worker публикует `order.created.v1` и отмечает событие опубликованным |
| AC-08 | При ошибке RabbitMQ неопубликованное событие остаётся в outbox |

## Статус реализации

В техническом прототипе реализуются только FR-03, FR-04, FR-05, FR-19 и FR-20. Остальные требования описывают следующие версии.
